Suggestions Board

Every suggestion below is a proposal only. Each one lists the problem, decision options with pros/cons, a recommended path, and what it unblocks. Nothing here is implemented — a reviewer picks an option (or defers) first. How to respond: record the chosen option in COORDINATION.md's request log (e.g., "S1 → option A"), then the implementing session executes it.

Review checklist per suggestion: ① Is the problem real (evidence linked)? ② Which option fits our constraints (no-manual-input goal, sandbox network limits, budget)? ③ What does it unblock, and what does it cost? ④ Approve / edit / defer.

S1 · Ingest game-level results for Weeks 1–9 high priority

Problem: ratings rely on aggregates only; parlay-outcome correlations and backtests are impossible without game rows (blank cells in the correlation matrix). Evidence: correlation-matrix.csv flagged rows.

Option A — GitHub-hosted dataset (nflverse) pulled via git/API. Pros: fits this environment's network rules (github.com reachable), free, historical depth, weekly automation via GitHub Actions. Cons: third-party compilation (must be labeled trusted tier, cross-checked vs NFL.com scores).

Option B — transcribe NFL.com weekly result pages manually each week. Pros: official-source purity. Cons: manual labor (violates the no-manual-input goal), error-prone.

Option C — defer. Cons: correlation cells stay blank; strategy gates G3/G6 stay blocked.

▶ Recommended: A with a verification step (weekly spot-check vs NFL.com game pages; mismatches → Flagged). Unblocks: SRS ratings, parlay correlations, backtesting, gates G3/G6.

Status: proposed — awaiting decision

S2 · Build the player-stat pipeline for prop origination high priority

Problem: player-prop combos (explicitly requested) cannot be originated or graded without player baselines (targets, snaps, usage). Evidence: Q7.

Option A — nflverse player-stats dataset (GitHub). Pros: same fit as S1; consistent schema. Cons: weekly update latency; trusted-tier labeling.

Option B — official NFL.com stats pages scraped per player. Pros: official. Cons: high fetch volume; no clean bulk export.

Option C — start with injury-driven prop signals only (no stat baselines). Pros: zero new data. Cons: prop lines can't be originated — only qualitative notes.

▶ Recommended: A, staged after S1 (shared infrastructure). Unblocks: prop origination, prop correlations, strategy class P.

Status: proposed — awaiting decision

S3 · Odds & closing-line feed high priority

Problem: we hold only snapshots; books disagree up to 3 pts (SEA-LV) and even on who is favored (CAR-NO). CLV gate (G4) has no closing line. Evidence: F4, F5, F6.

Option A — free aggregator API or weekly snapshot service. Pros: low cost, time-stamped. Cons: coverage varies; reliability needs monitoring.

Option B — paid odds API (e.g., commercial odds provider). Pros: full history, closing lines, multiple books. Cons: cost — needs budget decision (Q1-adjacent).

Option C — record our own daily snapshots from the five current sources. Pros: free. Cons: partial day coverage; manual-ish unless scripted — borderline vs no-manual-input goal.

▶ Recommended: A first, upgrade to B when stakes justify. Unblocks: gate G4, open-to-close signals, resolves Q10.

Status: proposed — awaiting decision

S4 · Depth-chart tier tie-break policy medium priority

Problem: club charts are self-labeled "unofficial", can be stale (MIN lists traded player), and can omit players who appear on official reports (Parsons/GB, Joseph/DET). Evidence: F1, F2, F3, F9.

Option A — hierarchy rule: coach statement > official game-status report > club depth chart > media. Pros: deterministic; matches how teams actually announce. Cons: coach statements need monitoring.

Option B — club chart always wins for tier; report wins for availability. Pros: simple separation (tier vs status). Cons: stale charts keep wrong tiers.

Option C — flag everything ambiguous and keep tiers blank. Pros: maximally honest. Cons: deficiency scores thin out.

▶ Recommended: A, with every applied tie-break recorded in the Flagged page log. Unblocks: Q4, sharper deficiency scores.

Status: proposed — awaiting decision

S5 · Recover depth data for HOU & SF medium priority

Problem: HOU publishes its chart as an image (not machine-readable); SF's depth page returned HTTP 500 on two attempts. These teams have major Week 10 absences. Evidence: F7, F8.

Option A — fetch alternate official surfaces (club roster pages, transactions) and reconstruct tiers from jersey/roster order + beat-writer confirmations. Pros: restores coverage. Cons: reconstruction is inference-adjacent — would need its own verification rules (only "confirmed" rows enter tables).

Option B — wait for SF page to recover; manually transcribe the HOU image once with dual verification. Pros: keeps "verified" bar. Cons: one-time manual step.

Option C — leave blank. Pros: zero risk. Cons: user requirement (defense deficiency tracking) unmet for two key teams.

▶ Recommended: B (small, verified, one-time), then A as a fallback process. Unblocks: Q11.

Status: proposed — awaiting decision

S6 · Contest integrity & skill-scoring thresholds medium priority

Problem: leaderboard entries must be time-stamped pre-kickoff and ranked by skill, not luck. Evidence: Q8, Q12; scoring design on Leaderboard.

Option A — git-committed entries + pre-registered thresholds (min 50 graded bets, FDR-corrected p<0.05, positive CLV average). Pros: tamper-proof timestamps (this repo is the ledger); thresholds battle-tested in the literature. Cons: 50-bet minimum means nothing ranks early in a season.

Option B — allow provisional ranking on smaller samples with wide uncertainty bands shown. Pros: engagement early. Cons: invites luck-chasing.

Option C — both: provisional list (clearly badged) + official list after gates. Pros: balances. Cons: two leaderboards to maintain.

▶ Recommended: C with A's thresholds for the official list. Unblocks: Q8, Q12.

Status: proposed — awaiting decision

S7 · Owner parameters: bankroll, rewards, jurisdiction high priority

Problem: Q1/Q2/Q9 cannot be answered from public data — they are owner decisions. Without them, staking rules and rewards are undefined.

Option A — conservative default pack: paper contest only, 1-unit flat stake, recognition rewards (badges + season trophy), no cash pool. Pros: zero legal/budget exposure; starts immediately. Cons: less motivation if cash was desired.

Option B — cash prize pool with % of bankroll as units, season-end payout. Pros: real incentive. Cons: needs budget + jurisdiction confirmation first.

Option C — hybrid: weekly non-cash badges + optional season prize once jurisdiction clears. Pros: staged. Cons: more rules to write.

▶ Recommended: A to launch now, revisit with B/C once parameters are provided. Unblocks: Q1, Q2, Q9.

Status: proposed — awaiting decision
