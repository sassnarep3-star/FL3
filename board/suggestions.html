Suggestion register

This is the section you asked for: suggestions on how to improve the site and the system, collected so a best path can be chosen before anything is implemented. Nothing in proposed status has been built; the six rows marked implemented-in-v1 were the minimum needed to make the rest auditable (row provenance, badges, the comparison layout, the review queue, regeneration and the reward formula).

Each row is written so it can be decided without a meeting: the problem it solves, the proposal, the impact, the effort, the risk, what it depends on, and whether we recommend it.

To decide: set data/suggestions.csv → owner_decision to approved: <date>, rejected: <reason> or defer, and commit. status moves to approved only in the same commit, so the register is also the decision log. (See S-05 for a one-click version of that.)

Explicitly not recommended (yet)

  • S-23 weather, S-07 model-health page, S-22 changelog - useful later, and if built now

they add a way to look busy while the inputs are still provisional.

  • Any signal-to-money path. No signal in the catalogue has passed a gate; the

correct use of the current pipeline is elimination, not staking.

What each type of suggestion is for

  • SITE - the review surface: how you see verification, deltas and decisions without reading CSVs.
  • DATA - inputs that do not exist in the repo yet, each with the exact source to obtain it from.
  • MODEL - changes to how a line is produced (all of which are blocked on the DATA rows).
  • PROCESS - the anti-luck machinery: grading, walk-forward discipline, multiple-comparison control,

bet ledger. This is the category with the highest value-per-dollar, because it is what prevents a lucky month from becoming a strategy.

  • OPS - bankroll, limits, and the human decisions that no pipeline can make for you.
