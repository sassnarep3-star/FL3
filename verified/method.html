Method & sources

What counts as evidence here, how a number gets on a page, and what was tried and rejected. Written so that a reviewer can check any claim on this site without taking its word for anything.

The source policy, in one paragraph

Only NFL-operated properties count as evidence: nfl.com (schedules, scores, standings, injuries, rosters, stats) and operations.nfl.com (rules). A club-operated page counts as evidence for facts only the club publishes — its own depth chart — and is labelled as club-published. A third-party aggregator, a DFS projection, a public consensus line and a sportsbook page are not evidence for an official value. Where a value can only be had from a non-official source, it is either labelled as a model estimate or left blank. It is never presented as a league fact.

How a row gets on a page

  1. Read the official page. Record the URL and the clock time.
  2. Transcribe, do not infer. If the page does not state it, it does not go in.
  3. Cross-check against a second official page wherever one exists. The results corpus is checked against the standings page club by club, 160 figures, no tolerance.
  4. Hash the artefact. The corpus hash is printed on Results.
  5. Render the source link with the value. A row without an official source renders a visible marker, and the build counts them.

Rejected sources, and why

CategoryWhy it is not used for an official value
Sportsbook and aggregator oddsNot league-operated, not licensed for retention or redistribution, usually geo-gated and not machine-readable. Used by no page on this site. Market columns are blank rather than filled from these.
Third-party depth chartsClub-adjacent but not official. Where they are used at all, they are labelled a model input and never a fact.
Projection and DFS sitesModel output of another party; cannot be evidence for a league value.
Memory and prior-season knowledgeNot a source. Roster turnover makes a remembered depth chart wrong; anything not read from a page today is not on this site.

The snapshot protocol this repo should have had from day one

Three of the ten open requirements are blocked only because a series was never captured. The fix is a schedule, not a model:

  • Daily, Wed–Sun capture of nfl.com/injuries/league/2026/reg10 with the fetch clock time, byte count and SHA-256 retained, so designations can be replayed as they were known.
  • Weekly capture of every club roster and depth page, versioned against the last official roster event rather than trusted as durable.
  • Post-game capture of the official game book for starters and game-day status.
  • Drift alarm on every parser: pin expected row counts and required fields, and fail loudly when a field disappears rather than publishing a blank.

None of this is claimed as done. It is the specification for the next session, written down so it is not re-derived.

Reproduce everything on this site

python3 scripts/build_week_results.py      # results corpus + identity check
python3 scripts/score_lines.py             # out-of-sample evaluation
python3 scripts/verify_live.py             # live re-verification register
python3 scripts/preregister_model.py       # registered model, hashed
python3 scripts/build_verified_site.py     # render this site
python3 scripts/check_verified_site.py     # assert sources, links and arithmetic

Deterministic: no randomness except the bootstrap, which is seeded. A re-run produces identical files, and CI fails the build if it does not.

What this is. A verified-data dashboard. Official league values carry a source link. Model output is labelled model output. No licensed betting price exists in this repository, so closing-line value and realised return are not computed and not implied anywhere.

Every page here is generated from the committed data files by scripts/build_verified_site.py and re-checked by scripts/check_verified_site.py. Other dashboards in this repository (root, board, docs, depth, site-9b181d31) are separate builds and are not superseded by this one.
